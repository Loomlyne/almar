## Decisions this plan takes

| Item | Decision | Why |
|---|---|---|
| Carrying the email (P5-09) | **Session storage**, key `almar.ops.bookings-search`, read once on mount of Bookings and removed at that read. | The row is a button with no href, and Bookings leaves that text out of its `replaceState`. **This replaces 05-01's `?q=` line only.** `bookings-screen.tsx` line 82 writes any applied search into the URL, so a storage handoff alone would not be enough: Task 3 changes that line for the handed text. |
| What stays as today | Text the owner types in the Bookings search still goes in `?q=`. The same-origin API call is still `GET /api/ops/bookings?q=`, as 05-01's list contract. | Not this plan's to change. Named in "Limits". |
| Back from a booking | Opening a row from a handed list puts the text back in storage, so Back on the detail page (`router.push("/dashboard/bookings")`) returns to that guest's bookings. | Otherwise one click loses the search. |
| Email over 100 characters | Hand off the first 100 characters. | `ListTable` always makes a row a control, so 05-01's "no link" would show a dead button (C-18). The search matches a substring, so the row still finds that guest. |
| Home's links (P5-08) | All three link to plain `/dashboard/bookings`, **no filter carried**. | The list's filters are text, status, destination and arrival dates. None matches "created in the range", "received in the range" or "still due"; a filter passed anyway would show a list that does not add up to the number. No new filter is added. |
| "Filled" number | Bookings above 0; Recorded when received or refunded is above 0 (recorded can net to 0 or below); Outstanding when `outstanding_count` is above 0. Otherwise plain text. | P5-08, "a filled number". |
| Custom range | Choosing Custom shows `DateRangeField`. The numbers stay on the last answer, with its own dates shown, until both days are picked. | The dates printed under the toggles always come from the answer, so nothing misleads. |
| Failed read | Numbers and rows are cleared, the sentence shows. | Same rule as Bookings: never an old answer under a failed one. |
| Canvas differences | `DashHome` draws comparisons, Recent bookings, Arrivals, Needs attention and Activity; `DashCustomers` draws Total spent, an All customers select and New customer. **None is built.** Card and row look comes from the canvas. | P5-01, P5-08, P5-09 narrow them. |
| Date toggles | Kit `Chip` with `on` and `onClick`, replacing the raw buttons. | Kit components only. |
| Profile monogram | Kept as drawn, decorative, `alt=""`. | P5-10 does not remove it. |
| Reminders and sign-out words | `noRemindersYet` and `newCustomer` leave `dashboard.ts` (only these screens used them). `signOut`, `logoutAll`, `signOutOfThisSite`, `signOutEverywhere`, `staySignedIn` stay: the rail uses them. | "Old unused copy cleaned only where this plan touches it". |

## Limits to know

- The list search matches a substring: `a@x.com` also shows `aa@x.com`. The handed email is visible in the search box, and the owner can see each row's guest.
- Bookings also lists TEST bookings, marked; the customer count leaves them out. So a row's count can be lower than the list it opens.
- Forward in the browser, or a reload, after the handoff shows the unfiltered list, since the handed text was read once.
- If session storage throws (blocked), the row still opens Bookings, unfiltered.
