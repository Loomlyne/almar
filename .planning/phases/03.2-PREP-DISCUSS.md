### 3.2 Where EN / AR / ES live: four options

Needs: three languages on every text; Arabic is RTL; alt text in three languages; images with text have three files; `PROJECT.md` and `I18N-04` want "ops types English, Publish fills AR and ES, editable, lockable, re-translate on English change unless locked", which means a per-language, per-field state (locked, reviewed, source changed).

| Option | Shape | One-sentence trade-off |
|---|---|---|
| **A. A translations table per entity (recommended)** | Base table holds the non-text facts (guests, rates, status); `stay_translations(stay_id, locale, name, tagline, description, seo_title, seo_description, locked, reviewed, source_hash)` holds one typed row per language | Typed columns and a lock/review flag per language make publish rules, SEO-required and a fourth language easy, at the cost of one join on every public read and 3 rows per item. |
| B. Three columns on the main row | `name_en, name_ar, name_es` on every translatable field | Simplest read and RLS, but every field triples, a lock flag per field per language multiplies columns again, and a fourth language is a migration. |
| C. One `jsonb` per field, `{en, ar, es}` | `name jsonb` | No migration to add a field or a language, but no column types, no `not null` per language, and locks and "required to publish" become application code that the database cannot enforce. |
| D. One generic table (entity type, id, locale, field, value) | a single `translations` table for everything including blog and legal | Fewest tables and one publish code path, but nothing is typed, nothing is a foreign key, and "SEO required to publish" cannot be a database rule. |

"One row per language for the whole record" is not a real option: it would copy rates, capacity and connections three times.

### Leftover 5. `harness-client.tsx` pulls fixtures into the production build
