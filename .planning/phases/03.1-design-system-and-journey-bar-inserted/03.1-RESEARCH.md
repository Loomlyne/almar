## Summary

This phase has two work surfaces that do not share tooling: the **claude.ai Design canvas** (owner-edited, outside the repo, produces `.dc.html` board exports) and the **repo** (Tailwind v4 conversion + coded journey components). The canvas work is not automatable from this session — it is done by the orchestrating Claude session and gated per page by the owner. The repo work is: generate `@theme` tokens from `tokens.json`, convert 6,183 lines of `app/globals.css` plus 15 CSS modules into component-scoped Tailwind utilities with `cva` + `tailwind-merge`, delete `/design` and `/framer`, merge `next.config.js`/`.mjs`, and build 11 journey components proven in a route-less Playwright harness against canvas screenshots.

The single highest-risk finding: **`@playwright/experimental-ct-react` is dead** — the package's last published version is `1.62.1` and the repo already has `@playwright/test@1.63.0` installed, one minor ahead of the last version that ecosystem tooling still expected it to work with. Playwright removed the experimental CT packages in favor of a framework-agnostic "gallery" pattern using `fixtures.mount()` served by the app's own dev server. Do not plan any task around `@playwright/experimental-ct-react` — plan a route-less test harness page instead (Section: Code Examples).

The second highest-risk finding: `tailwind-merge` does not know about this project's custom `@theme` tokens (`--text-body`, `--text-label`, `--color-teal`, etc.) out of the box. Without `extendTailwindMerge({ extend: { classGroups: {...} } })`, any `cva()` variant that conditionally swaps a custom class (e.g. `text-body` vs `text-title`) will be silently dropped or wrongly deduplicated by `twMerge`. This must be a named task, not an afterthought.

**Primary recommendation:** Treat 3.1 as two independently-gated tracks that share only `tokens.json`. Track A (canvas) is owner-paced and out of this session's control — plans should list canvas pages as `checkpoint:human-verify` gates per D-09/D-35 pages, not as automatable tasks. Track B (repo) follows D-31's fixed order: `tokens.json` → `@theme` generation script → guardrail test (arbitrary-value / physical-utility / hex ban) → Tailwind conversion of globals.css/modules → logos/next.config.ts/team removal/`/design`+`/framer` deletion → 11 coded components → route-less Playwright harness screenshots.

### Pattern 1: `@theme` generation keeps CSS custom properties (runtime overridable)
**What:** Generate `app/globals.css`'s `@theme {}` block from `tokens.json` at build/dev time, not by hand-editing CSS.
**When to use:** Any token addition/change.
**Why it matters here:** D-11 requires tokens to remain CSS custom properties so Settings → Brand (Phase 5, DSGN-04) can override them at runtime via `document.documentElement.style.setProperty(...)`. Tailwind v4's `@theme` directive already compiles token declarations to real CSS custom properties on `:root` (this is Tailwind v4's own design, not a workaround) — so writing tokens inside `@theme {}` (as `app/globals.css` already does) satisfies D-11 without extra plumbing. Do not resolve tokens to hard-coded values in generated Tailwind classes.
```css
/* Source: existing app/globals.css, extend this pattern with a generation script */
@theme {
  --color-teal: #1f3b40;      /* becomes var(--color-teal), usable in bg-teal, text-teal, etc. */
  --text-body: 16px;           /* becomes var(--text-body), usable in text-body */
}
```

### Pattern 2: `cva()` + `twMerge()` for JourneySegment states
**What:** Encode D-36's 5 states (Empty, Hover, Open/focus, Filled, Missing) as a `cva()` variant map, not conditional className strings.
**When to use:** Every component with named states in the CONTEXT.md decisions (D-36, D-46 stepper states, D-51 StepRail marks).
```typescript
// Pattern — no official source (cva has no Context7 entry checked this session); based on cva's documented API shape
import { cva, type VariantProps } from "class-variance-authority";
import { twMerge } from "tailwind-merge";

const segment = cva(
  "h-[72px] px-6 flex flex-col justify-center gap-0.5 border border-line",
  {
    variants: {
      state: {
        empty: "bg-ivory",
        hover: "bg-white",
        open: "bg-white shadow-[inset_0_-3px_0_var(--color-teal)]",
        filled: "bg-ivory",
        missing: "bg-ivory shadow-[inset_0_-3px_0_var(--color-error)]",
      },
    },
    defaultVariants: { state: "empty" },
  },
);

export function JourneySegment({ state, className, ...props }: VariantProps<typeof segment> & { className?: string }) {
  return <div className={twMerge(segment({ state }), className)} {...props} />;
}
```
**Critical caveat (see Pitfall 2):** `twMerge` must be configured with `extendTailwindMerge` to recognize `--text-*` custom theme tokens, or it will misresolve `text-body`/`text-title` conflicts.

### Pattern 3: Logical properties for RTL, enforced by the guardrail test
**What:** All spacing/positioning uses `ms-*`/`me-*`/`ps-*`/`pe-*`/`start-*`/`end-*` and `rtl:` variants; never `ml-`/`mr-`/`pl-`/`pr-`/`left-`/`right-`/`text-left`/`text-right`.
**When to use:** Every new component; this is D-29's second guardrail category and directly serves DSGN-03.
```tsx
// Source: Tailwind v4 docs pattern (logical properties are Tailwind's default naming for RTL-aware utilities)
<div className="ms-4 pe-6 text-start">
  {/* ms-4 = margin-inline-start, pe-6 = padding-inline-end, text-start = text-align: start */}
</div>
```

### Anti-Patterns to Avoid
- **Arbitrary Tailwind values (`bg-[#1f3b40]`, `text-[13px]`):** Bypasses the `@theme` token layer entirely; D-29's guardrail test must fail the build on these. Every value must resolve to a named token (D-19's 7 type steps, D-12's palette).
- **`*.module.css` co-located with a converted component:** D-26 says no `*.module.css` remains after conversion — leaving one behind for "just this one tricky bit" defeats D-27's stated end-state (globals.css only has `@import` + `@theme` + minimal `@layer base`).
- **Hard-coded EN copy or seeded catalog data inside a journey component:** Violates D-33 directly. Components take `destinations`, `addOns`, `inclusions`, `prices`, `team` as props; fixtures live in tests/canvas only.
- **`.nav-tools`-style parent-dependent selectors:** D-27 explicitly bans styles that depend on a parent class. The language/currency select (D-60) must work with no parent-scoped CSS.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Class-name conflict resolution when variants compose | A custom "last class wins" string merger | `tailwind-merge` (`twMerge`), configured with `extendTailwindMerge` for custom `@theme` tokens | Naive string concatenation lets `p-2 p-4` both reach the DOM (unpredictable which wins depending on CSS source order); twMerge resolves by Tailwind class *group*, not string order |
| Plural/list guest-count string ("2 adults, 1 child, 1 infant") in EN/AR/ES | Manual if/else pluralization per locale | `Intl.PluralRules` (per-locale plural category) + `Intl.ListFormat` (per-locale list joining, handles Arabic's right-to-left/oxford-comma-equivalent conventions) | Arabic has 6 grammatical plural categories (zero/one/two/few/many/other); a manual EN-style "if count===1" check silently produces wrong Arabic grammar. Both are built into V8/Node since Node 13, zero install cost. |
| Calendar day math (min-nights, past-day disabling, range selection) | Custom Date arithmetic | `@internationalized/date` (already installed, already used in `components/ui/calendar.tsx`) | Calendar math across DST, locale week-start (Monday per D-40), and Gregorian-only display is already solved in the codebase; `DateRangePanel`/`DayCell` should call into the same calendar utilities, not reimplement them |
| Focus trap / listbox keyboard nav for `DestinationMenu`, `JourneySheet` | Custom `keydown` handlers | `radix-ui` (already installed) `Dialog`/`Listbox`/`Popover` primitives | Radix already handles ARIA roles, focus return, Escape-to-close, and typeahead — re-implementing risks missing an a11y edge case D-32/DSGN-05 require |
| Arbitrary-value / physical-utility detection | A bespoke regex maintained ad hoc per PR | Extend the existing `tests/design-tokens.test.mjs` pattern (it already walks `app/globals.css`, `app/layout.tsx`, `app/design`, `components` and bans a hardcoded string list) | The repo already has this exact mechanism (banned-string scan over stripped-comment source); D-29 is naturally an extension of it, not a new tool |

**Key insight:** Every "don't hand-roll" item above already has a matching library or pattern present in this repo. The phase's risk is not missing tooling — it's *not wiring the tooling together correctly* (twMerge + custom tokens, cva + state variants, the existing token test extended rather than duplicated).

## Common Pitfalls

### Pitfall 1: Planning around `@playwright/experimental-ct-react`
**What goes wrong:** A plan task says "set up Playwright component testing" and a subagent installs `@playwright/experimental-ct-react`, which either fails to install cleanly against `@playwright/test@1.63.0` or installs a stale `1.62.1` that immediately conflicts with the test runner version already in `package.json`.
**Why it happens:** Training data (and much still-online tutorial content) describes `@playwright/experimental-ct-react` as the standard way to do React component testing with Playwright; it was never marked `deprecated` in npm metadata (checked this session — no `deprecated` flag set), so `npm view` alone doesn't warn you.
**How to avoid:** Plan tasks explicitly for a **route-less harness page** approach: a Next.js route (e.g. `app/__harness/journey/[component]/page.tsx`, excluded from the production sitemap/robots and gated behind `NODE_ENV !== "production"` or a build-time route filter) that renders each journey component with fixture props based on a `?state=` query param, then standard `@playwright/test` `page.goto()` + `page.screenshot()` against it. This is the pattern Playwright itself now documents as the "gallery" replacement.
**Warning signs:** Any task or code mentions `experimental-ct-react`, `playwright-ct.config.ts`, or `import { test } from "@playwright/experimental-ct-react"`.

### Pitfall 2: `twMerge` silently drops or misresolves custom `@theme` classes
**What goes wrong:** A `cva()` variant conditionally applies `text-title` in one state and `text-body` in another; a caller passes an override `className="text-heading"`; `twMerge` (unconfigured) doesn't recognize any of `text-body`/`text-title`/`text-heading`/`text-display`/`text-hero`/`text-caption`/`text-label` (D-19's 7-step scale) as belonging to the same conflict group as Tailwind's built-in `text-*` size utilities, so either (a) it treats them as unrelated and both survive, producing wrong rendered type, or (b) it treats them as unrelated to color `text-*` utilities and a `text-teal` color class gets wrongly merged away thinking it conflicts with `text-body`.
**Why it happens:** `tailwind-merge`'s default config maps class groups by pattern-matching Tailwind's *default* theme scale names; it has no knowledge of project-specific `@theme` extensions unless told explicitly via `extendTailwindMerge`.
**How to avoid:** One task, early in the conversion (before component work begins): create `lib/tw-merge.ts` exporting a configured `twMerge` that registers the 7 type-step classes as a `font-size` group and the 12-ish palette tokens as `text-color`/`bg-color`/`border-color` groups. Every component's `cn()`/merge helper imports from this file, not raw `tailwind-merge`.
**Warning signs:** Visual regression in the Playwright harness shows a component rendering with the *wrong* type size or color despite the `cva()` variant map looking correct in code review.

### Pitfall 3: `.module.css` files quietly reintroduced during "quick fixes"
**What goes wrong:** Mid-conversion, a task needs a CSS feature Tailwind utilities don't cleanly express (e.g. a complex `:has()` selector or a multi-step `@keyframes`), and the fastest fix is "just add a small module.css for this one component" — directly violating D-26's "No `*.module.css` remains" end-state, and it's easy to miss in review because it looks like a reasonable engineering call.
**Why it happens:** Tailwind utility classes genuinely don't cover every CSS feature (complex animations, `:has()`, container queries needing named containers) as cleanly as authored CSS.
**How to avoid:** For animation, D-44 already specifies motion tokens (`--duration-fast/mid/slow`, `--ease-standard`) — express keyframes via Tailwind's `@theme` `--animate-*` mechanism (v4 supports defining named animations in `@theme` that become `animate-*` utilities) rather than a module.css keyframe block. For anything else, the guardrail test's file-scan (Pattern 3 above) should be extended to also flag any newly-created `*.module.css` file under `components/` or `app/` outside an explicit allowlist, so reintroduction fails CI immediately rather than being caught in human review.
**Warning signs:** `git status` during a conversion PR shows a new `.module.css` file.

### Pitfall 4: `app/embed/hero-booker/route.ts` and `app/framer/source/route.ts` are NOT in D-34's explicit deletion list but both import files scheduled for removal
**What goes wrong:** D-34 names `app/design/**` and `app/framer/**` for deletion. `lib/framer-hero-booker-mount.tsx` (imported by both `app/embed/hero-booker/route.ts` and `app/framer/source/route.ts`) mounts `components/specimens/hero-booker.tsx` into the *live* Framer HTML via an injected script bundle built by `app/framer/inject-hero-booker.ts`. If `/framer` is deleted without checking `app/embed/hero-booker/route.ts` (which is outside `app/framer/`), that route silently breaks or references a now-deleted mount file.
**Why it happens:** The embed route lives at a different path (`app/embed/`) than the deletion targets (`app/framer/`, `app/design/`), so a literal reading of D-34 misses it.
**How to avoid:** Before deleting `/framer`, `grep -rn "framer-hero-booker-mount\|hero-booker-style\|inject-hero-booker"` across `app/` and `lib/` and confirm what `app/embed/hero-booker/route.ts` is actually for (it serves a JS bundle that the *live Framer `route.ts` HTML* injects to mount the React hero-booker inside the still-live Framer page). This route currently exists to make the live `/` Framer page interactive — it is **not** part of `/design` or `/framer` (the dev/preview routes) and must NOT be deleted in 3.1; it stays live until 3.3 replaces the home page. Add an explicit task: "confirm `app/embed/hero-booker/route.ts` and its dependency chain survive `/framer` (dev route) deletion, since it depends on `components/specimens/hero-booker.tsx` which IS being converted to Tailwind in this phase — the embed bundle must still build after conversion."
**Warning signs:** Live `/` (Framer HTML, untouched by this phase) loses its interactive hero booker after this phase ships.

### Pitfall 5: Deleting `/design` breaks 4 existing test files, not just the 4 `design-*.spec.ts` files
**What goes wrong:** `tests/design-a11y.spec.ts`, `tests/design-page.spec.ts`, `tests/design-rtl.spec.ts`, `tests/design-video.spec.ts` obviously test the `/design` route and must be replaced/removed. Less obviously, `tests/design-tokens.test.mjs` has `"app/design"` hardcoded in its `SCOPES` array (used to build the banned-string corpus), and `tests/phase-03-newsletter.test.mjs`, `tests/phase-03-guest.test.mjs`, `tests/phase-03-search.test.mjs` also reference `app/design` or `app/framer` paths.
**Why it happens:** `/design` was Phase 1's "owner can see every component" specimen page (DSGN-01); many later phase tests reused it as a convenient fixture surface rather than testing real routes.
**How to avoid:** Task explicitly: `grep -rln "app/design\|app/framer" tests/` before deleting the routes, and update or repoint each match. `tests/design-tokens.test.mjs`'s `SCOPES` array should drop `"app/design"` and (if intended for DSGN-01 compliance going forward) should NOT be repointed at the canvas — DSGN-01 itself is superseded in spirit by D-02 ("the canvas is the primary design system... I don't want to say /design anymore"), so this guardrail test's purpose narrows to guarding `app/globals.css`, `app/layout.tsx`, and `components/`.
**Warning signs:** `npm test` fails after `/design` deletion with `ENOENT` on `app/design`.

### Guest count string — Intl.PluralRules + Intl.ListFormat (D-41)
```typescript
// Source: MDN Intl.PluralRules / Intl.ListFormat (built into Node/V8, no package) —
// [CITED: developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules]
// [CITED: developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/ListFormat]
type GuestCounts = { adults: number; children: number; infants: number };
type Locale = "en" | "ar" | "es";

const LOCALE_TAG: Record<Locale, string> = { en: "en", ar: "ar", es: "es" };

const UNIT_LABEL: Record<Locale, Record<"adults" | "children" | "infants", Record<string, string>>> = {
  en: {
    adults: { one: "adult", other: "adults" },
    children: { one: "child", other: "children" },
    infants: { one: "infant", other: "infants" },
  },
  // ar/es filled from lib/copy/journey.ts — Arabic needs "two" (dual) and "few"/"many" categories
  ar: { adults: {}, children: {}, infants: {} } as any,
  es: { adults: {}, children: {}, infants: {} } as any,
};

export function formatGuestSummary(counts: GuestCounts, locale: Locale): string {
  const pluralRules = new Intl.PluralRules(LOCALE_TAG[locale]);
  const listFormat = new Intl.ListFormat(LOCALE_TAG[locale], { style: "long", type: "conjunction" });

  const parts: string[] = [];
  for (const key of ["adults", "children", "infants"] as const) {
    const n = counts[key];
    if (n <= 0) continue; // D-41: only non-zero groups are listed
    const category = pluralRules.select(n); // "zero" | "one" | "two" | "few" | "many" | "other"
    const label = UNIT_LABEL[locale][key][category] ?? UNIT_LABEL[locale][key].other;
    parts.push(`${n} ${label}`);
  }
  return listFormat.format(parts); // "2 adults, 1 child, 1 infant"
}
```
**Note:** Arabic dual (`category === "two"`) and Western numerals (D-40/D-41 require `ar-AE-u-nu-latn` per the existing `LATN` constant in `lib/format.ts`) mean the number itself must still be formatted via `Intl.NumberFormat("ar-AE-u-nu-latn")` if displayed standalone — `Intl.PluralRules` only selects the *grammatical category*, it does not format the digit string. Reuse `lib/format.ts`'s existing `LATN` locale tag for any Arabic digit display in this component.

### `tokens.json` → `@theme` generation (minimal script, per D-11's runtime-override requirement)
```javascript
// scripts/generate-theme.mjs — no official source, hand-rolled per project need (style-dictionary rejected, see Alternatives Considered)
import { readFileSync, writeFileSync } from "node:fs";

const tokens = JSON.parse(readFileSync("tokens.json", "utf8"));
const lines = ["@theme {"];
for (const [group, values] of Object.entries(tokens)) {
  for (const [key, value] of Object.entries(values)) {
    lines.push(`  --${group}-${key}: ${value};`);
  }
}
lines.push("}");
// Inject between markers in app/globals.css so hand-written @layer base below it survives regeneration
const css = readFileSync("app/globals.css", "utf8");
const updated = css.replace(
  /\/\* GENERATED:THEME:START \*\/[\s\S]*?\/\* GENERATED:THEME:END \*\//,
  `/* GENERATED:THEME:START */\n${lines.join("\n")}\n/* GENERATED:THEME:END */`,
);
writeFileSync("app/globals.css", updated);
```
**Design note:** Output stays inside `@theme {}` (not resolved to static values) specifically so Tailwind v4 compiles them to `:root` CSS custom properties — satisfying D-11's runtime-override requirement for Phase 5 without any extra "CSS variable shadow layer."
