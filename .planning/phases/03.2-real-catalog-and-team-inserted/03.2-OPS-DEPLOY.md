# Worker `almar-ops` deploy runbook, with the Free-plan CPU measurement

For the ALMAR controller only, on the owner's word for each step marked so. Written by plan 03.2-03, 2026-10-05, on the
model of `02-RUNTIME-DEPLOY.md`. Run every command from the main ALMAR folder on `main`, after 03.2-01 and 03.2-03 have
landed, with `npm ci` done. No work session runs any of it.

Every wrangler command is written out in full with ALMAR's own login. Never a bare `wrangler` (it is the Vamos login),
never `opennextjs-cloudflare deploy`, never an `npm run` deploy (there is none).

What this deploy creates: Worker `almar-ops` (new), with the custom domain `dashboard.almarprivatejourney.com` (the deploy
creates its DNS record) and three bindings: `ASSETS`, `AI` (Workers AI, for Translate), `MEDIA` (R2 bucket `almar-media`,
for uploads). What it does not touch: Worker `almar`, Worker `almar-preview`, their versions, secrets or domains.

There is **no preview copy** of `almar-ops` in v1. The only database is the live Supabase project, so a second ops Worker
would edit the same rows. `almar-ops` is owner-only behind sign-in, and the `OPS_LIVE_SECTIONS` gate (below) keeps
unwired screens hidden until a plan wires them.

## 5. CPU measurement (Workers Free, 10 ms per request)

**Timing:** run sections 0 to 5 right after wave 1 lands (03.2-01 and 03.2-03 merged on the 3.2a branch, built from that
commit in a clean clone, before 02, 04 and 05 are built), so the answer to the Workers Paid question is known while the API
and the screens are still being written. Put the question to the owner at that moment with the measured numbers
(research Open Question 7). Later plans re-run only their own lines of this section.

With the tail open (`--format json` gives one event per request with `outcome`, and `cpuTime` and `wallTime` in ms where the
event carries them; if it does not, read p50 and p99 CPU time for `almar-ops` in the dashboard, Workers & Pages,
`almar-ops`, Metrics):

1. `/sign-in` 20 times (section 4.2).
2. Signed in as the owner in his browser: reload `/` 20 times, and `/catalog/stays` 20 times (the shell's "Not ready."
   state; each screens plan repeats this for its own screen). Do the 20 reloads on one network, then 5 more from the phone
   on mobile data (a different network is a different isolate); repeat the whole of this after every `secret put` (each is a
   new version, which starts cold).
3. Record per request: the status, the CPU time. Write the median, the maximum and the count over 5 ms.

**Stop rule (owner D-SR-02):** any `exceededCpu`, `1102` or `503`: roll back (section 6) and put the Workers Paid question
to the owner with the numbers. Plans 03.2-04 and 03.2-05 add their endpoints to this section (`/api/ops/*`, site status).

The measured result goes on the board with the date and the version id.

## 6. Rollback

First deploy has no earlier version: a failing first deploy is undone by `delete` only, on the owner's word (it removes the
Worker and its custom domain; the public site is untouched):

```
HOME=/Users/koss/.almar-cloudflare CLOUDFLARE_ACCOUNT_ID=f1d9a1fa3abdda98c15161b00b40385c ./node_modules/.bin/wrangler delete --config wrangler.ops.toml
```

Once a second version exists (after a secret or a later deploy):

```
HOME=/Users/koss/.almar-cloudflare CLOUDFLARE_ACCOUNT_ID=f1d9a1fa3abdda98c15161b00b40385c ./node_modules/.bin/wrangler rollback <version id from 3> --message "almar-ops rollback" --config wrangler.ops.toml
```

Then repeat section 4.1 to 4.4. A rollback never touches `almar` or `almar-preview`.

## 7. After a good deploy

- The board records the `almar-ops` version id, the time and the section 5 numbers.
- `OPS_HOST_LIVE` in `lib/host.ts` is still `false`: this plan does not flip it (tests pin it). It gates the public account
  menu's dashboard link (TOUCHWORD) and `/auth/handoff/start` on the live site. Flip it in its own commit, and deploy
  `almar`, only after sections 4 and 5 passed. That is the controller's call and its own owner word.
- Workers Builds (plan 03.2-05) rebuilds `almar` only. `almar-ops` is dynamic and is deployed by hand, from a fresh
  `--target=ops` build, whenever its code changes.
- **Open item for plan 03.2-04 (its first POST endpoint):** job 10's runbook (`02-RUNTIME-DEPLOY.md`, section 6) records
  that `worker/handle.mjs` forwards `new Request(request, { headers })`, and that nothing has yet proven that a second POST in
  one session keeps its body once OpenNext has replaced `globalThis.Request`. `almar-ops` uses the same `handle.mjs`, and
  is the first Worker to take POST bodies. 03.2-04's built spec must send two POSTs with different bodies in one session
  and have the route echo a length or hash of what it read, before any `/api/ops/*` POST ships.
