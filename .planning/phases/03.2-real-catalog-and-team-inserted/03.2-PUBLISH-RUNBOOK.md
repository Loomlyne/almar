# Publish rebuild runbook (plan 03.2-05): production `almar` = branch `live`

For the controller. Research §1.3–1.5; decisions C-01…C-05. Every live step below waits for the owner's word, one numbered
step at a time. No secret value ever goes into chat, a file or the repo; names only.

## 1. The rule from now on

- **Production Worker `almar` is built and deployed only from GitHub branch `live`, by Workers Builds.** Every push to
  `live` builds and deploys `almar`; every owner write that reaches the public site (`affects_site: true`, and 02-06's
  settings through `requestPublish({ admin })`) fires the "Publish" Deploy Hook, which builds `live` again with the
  database content of that moment. A Publish click changes content only, never code (C-02): `scripts/build-live.mjs`
  refuses any branch but `live`.
- **The controller's code deploy** of `almar` becomes: clean-clone check of the commit (lockfile install, every gate, the
  build), the preview Worker as in job 10's runbook (`.planning/phases/02-platform-spine/02-RUNTIME-DEPLOY.md`), the
  dry-run size check, then, on the owner's word:

  ```
  git push origin ${commit}:refs/heads/live
  ```

  (zsh: keep the braces before the colon). The commit must be a landed `main` commit.
- **No manual `wrangler deploy` of `almar` any more.** A deploy of anything other than `live` HEAD is undone by the next
  Publish. `almar-preview` and `almar-ops` stay manual, as before.
- **Non-production builds are off.** If a push to another branch still starts a build of `almar` (a reported Workers
  Builds bug, research §1.1), cancel it in the dashboard (Workers & Pages → `almar` → Deployments → the build → Cancel)
  and tell the owner.
- **Content and the sequence.** `build-live.mjs` reads `api_site_version.requested_seq` after the settle sleep and before
  any content, and writes it to `out/site-version.json`; after 03.2-02b, the assembler also reads it before and after the
  build and fails if it moved. So a click during a build makes that build fail (the live site stays as it was) and the
  build its hook call queued deploys everything. The dashboard says "Updating" until a build carrying the newest
  sequence is live.

## 2. Rollback

Both, on the owner's word, or the next Publish brings the bad code back:

```
HOME=/Users/koss/.almar-cloudflare CLOUDFLARE_ACCOUNT_ID=f1d9a1fa3abdda98c15161b00b40385c ./node_modules/.bin/wrangler rollback ${version} --config wrangler.toml
git push --force-with-lease origin ${good_commit}:refs/heads/live
```

`${version}` comes from `wrangler deployments list --config wrangler.toml`, never from a file. Resetting `live` starts a
build of `${good_commit}`; that build is the lasting fix, the rollback only covers the minutes until it is live.

To stop all automatic builds at once (for example a leaked hook URL): Settings → Builds → Deploy Hooks → delete
"Publish" (every Publish then shows "Update failed" until step 3 is redone with a new hook), or Settings → Builds →
Disconnect.

## 3. Owner gate steps, one at a time, each waiting for his "done"

1. **Controller:** read the commit now live on `almar` (`wrangler deployments list --config wrangler.toml`, the newest
   version's message or tag; confirm it is a landed `main` commit with `git cat-file -e origin/main:<a file of it>` and
   `git merge-base --is-ancestor ${commit} origin/main`). On the owner's word: `git push origin ${commit}:refs/heads/live`.
   Expected: GitHub shows branch `live` at that commit. Nothing builds yet.
2. **Owner, Cloudflare dashboard, account "Almar Private Journey":** Workers & Pages → `almar` → Settings → Builds →
   Connect → GitHub → install the Cloudflare Workers & Pages app on `Loomlyne`, for repository `almar` **only** → then:
   - production branch: `live`
   - non-production branch builds: **off**
   - root directory: `/`
   - build command: `node scripts/build-live.mjs`
   - deploy command: `npx wrangler deploy --config wrangler.toml`
   - build variables (he types the values): `NODE_VERSION=24`, `ALMAR_PUBLISH_SETTLE_SECONDS=120`,
     `NEXT_PUBLIC_SUPABASE_URL` (the live project URL, `https://jkdkaldgeiowkhlfmsft.supabase.co`; 03.2-02b refuses any
     other host), `NEXT_PUBLIC_SUPABASE_ANON_KEY` (the publishable/anon key; never the service key: the assembler refuses
     a secret key and any `SERVICE_ROLE` variable).

   Expected: a first build starts and deploys the same code that is live (it counts as his deploy word). Its log shows, in
   order: `build-live: branch live; settling 120 s …`, `build-live: building publish sequence N`, the assembler's
   `assembled … (target: production)`, `build-live: wrote out/site-version.json (seq N, commit …)`, then wrangler's deploy.
   **If it stops at `builds only from branch live`:** the line above it lists the `WORKERS_CI*` names the image sets. Tell
   the work session (or fix in a quick job) which name carries the branch; `WORKERS_CI_BRANCH` is assumed (research §1.1).
3. **Owner:** Settings → Builds → Deploy Hooks → Create → name `Publish`, branch `live` → copy the URL, then in his own
   terminal (never pasted in chat or a file):

   ```
   HOME=/Users/koss/.almar-cloudflare CLOUDFLARE_ACCOUNT_ID=f1d9a1fa3abdda98c15161b00b40385c ./node_modules/.bin/wrangler secret put PUBLISH_DEPLOY_HOOK_URL --config wrangler.ops.toml
   ```

   It must start with `https://api.cloudflare.com/client/v4/workers/builds/deploy_hooks/`; any other value is never called
   (`error:bad_hook`). The `secret put` makes a new `almar-ops` version: read its id as the new rollback target
   (`03.2-OPS-DEPLOY.md` §3).

## 4. First checks (controller, read-only, after step 3)

1. `curl -s https://almarprivatejourney.com/site-version.json` returns `{"seq":N,"built_at":"…","commit":"…"}` with the
   sequence of the first build's log.
2. `curl -sI https://almarprivatejourney.com/site-version.json` shows `cache-control: no-store`.
3. Job 10's live checks (`02-RUNTIME-DEPLOY.md` §4) pass on the new version.
4. In the dashboard header the line reads "Up to date · <time of that build>".
5. **Owner UAT:** unpublish then publish one journey (or save a published stay). The line turns "Updating since <time>"
   at once, then "Up to date · <time>" (expected within about 8 minutes: 2 min settle + install and build), and the
   public page shows the change. Then the controller reads in the Cloudflare dashboard: the hook's answer fields
   (`build_uuid`, `already_exists`; `site_publish.last_hook_result` / `last_build_uuid` read-only from the live row),
   the build time, and the build minutes used (Free: 3,000 a month). Write them into `03.2-05-SUMMARY.md`.
6. Measure `/api/ops/site-status` per `03.2-OPS-DEPLOY.md` §5 item 5.

## 5. What the dashboard line means

| Line | Rule (`lib/ops/site-status.ts`) | What to do |
|---|---|---|
| Up to date · 14:05 | live `site-version.json` seq ≥ requested seq; time = when that build ran | nothing |
| Updating since 14:02 | behind, requested < 28 min ago, hook call did not fail | wait; it re-reads every 15 s |
| Update failed · 14:30 · Try again | hook call failed (`error:no_hook`, `error:bad_hook`, `error:<status>`, `error:network`), or still behind 28 min after the request | Try again fires the hook once more; if it fails again, open the build log in Workers & Pages → `almar` → Deployments |
| Status unavailable | `/api/ops/site-status` did not answer | check `almar-ops` (tail) |
