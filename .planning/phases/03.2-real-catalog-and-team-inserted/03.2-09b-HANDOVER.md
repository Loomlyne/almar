## What changed, per finding

### 1. One 10 MB limit end to end
- Why 10 MB and not "set the option and drop the route from the matcher": `middleware.ts` must run on
  `/api/ops/media`. It sets `x-almar-shell: ops`, and `requireOwner()` (`lib/auth/require-owner.ts:21`) reads that header;
  without the middleware every owner call is 403. So the matcher and `next.config.ts` are unchanged.
- Where Next's limit is set: `node_modules/next/dist/server/body-streams.js:30`,
  `const DEFAULT_BODY_CLONE_SIZE_LIMIT = 10 * 1024 * 1024 // 10MB`, used by `cloneBodyStream()` (line 85,
  `sizeLimit ?? DEFAULT_BODY_CLONE_SIZE_LIMIT`; `sizeLimit` is `experimental.middlewareClientMaxBodySize`, not set in
  `next.config.ts`). It cuts only when `bytesRead > bodySizeLimit` (line 90), so exactly 10 MB passes whole.
- Where that limit applies: the Node server with in-process middleware (`next dev`, `next start`). On Cloudflare the
  middleware is external (`.open-next/middleware/open-next.config.mjs`: `middleware: { external: true }`); the clone is
  never made there (see "Grok's medium" below). On Cloudflare OpenNext reads the whole body into memory instead, so
  10 MB is the memory bound of one upload there. One limit for both runtimes.
- Real PUTs on the built `almar-ops` Worker (`wrangler dev`, local stack, owner session; `tests/build/media-put-cpu.mjs`):
  exactly 10,485,760 bytes → 200 stored; 10,485,761 bytes → 413 `too_large`, field null (3 of 3 each, in each of three runs).
- `MAX_UPLOAD_BYTES` 15 → 10 MB in `lib/ops/validate-media.ts` (server, 413 on the header),
  `components/ops/media-types.ts` and `components/ops/image-prep.ts` (`MAX_BYTES`, the re-encode check).
- `lib/copy/ops-media.ts`: the number only, 15 → 10, in EN, AR and ES (`uploadHint`, `tooLarge`), as approved.
- A body over 10 MB is refused on its `Content-Length` (413 `too_large`, field null) before a byte is read, so it is
  never a cut-off upload; the screen shows `tooLarge`.

### 2. Size checked after the re-encode only
- `components/ops/use-media-library.ts`: `onPickFile` no longer refuses `picked.size > MAX_UPLOAD_BYTES`; the type
  check stays. The only size check is `image-prep.ts:125` (`blob.size > MAX_BYTES` → `too_large` → `copy.tooLarge`).

### 3. The list is paged and searched in SQL
- New migration `supabase/migrations/20261012120000_ops_list_media.sql` (number approved by the controller):
  `public.media_fold(text)` (NFD, combining marks removed, lower case) and
  `public.ops_list_media(p_q text, p_after text, p_limit int)` → `{items, next}`. Items have the exact shape of an
  `ops_list('media')` row. Byte key order (`collate "C"`) then id; `q` over the key and the English alt only, plain
  `strpos` (no LIKE wildcards); a page never ends between two rows of one imported key; `next` = the page's last key or
  null. Validates `p_limit` 1..60, `p_q` ≤ 100 characters, `p_after` as a media key (P0001 `almar:invalid`).
- Grants: `revoke execute … from public, anon, authenticated; grant execute … to service_role` on both functions.
  `create or replace` only; no table, row or existing function is touched (`ops_list('media')` is unchanged and still
  used by nothing else in this route). **Safe on live data.**
- `lib/ops/media-upload.ts`: `listMedia({ listPage, url })` passes the checked query to the database and maps one page;
  the Worker-side fold/sort/filter (`mediaPage` over the whole library) is gone.
- `app/api/ops/media/route.ts`: GET calls `rpc("ops_list_media", { p_q, p_after, p_limit })`.

### 4. Content sniffing
- `lib/ops/validate-media.ts`: `hasSignature(bytes, type)` — JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, WebP
  `RIFF` + 4 bytes + `WEBP`; `SNIFF_BYTES = 12`.
- `lib/ops/media-upload.ts` `uploadCore`: for a new key, `sniffBody` reads only the first 12 bytes, checks the
  signature, then streams those bytes and the rest, in order, through the length stream into R2 (no whole-body read).
  A mismatch is 415 `wrong_type` (the screen shows `wrongType`); nothing is put or saved and the rest of the body is
  cancelled. A body that ends before 12 bytes (and before Content-Length) is 400 `content_length`, as before.
- **`X-Content-Type-Options: nosniff` on the media host is not code in this repo.** `media.almarprivatejourney.com` is
  the R2 bucket's custom domain; R2 object metadata cannot carry that header. Live check (plain GET, 2026-10-13) of
  `https://media.almarprivatejourney.com/home/hero/poster.webp`: 200, `content-type: image/webp`,
  `cache-control: public, max-age=31536000, immutable`, **no** `x-content-type-options`. Controller step below.

### 5. Two uploads of one file at once
- `lib/ops/media-upload.ts` `uploadCore`: when `ops_save_media` answers 23505 (both uploads found no row; the second
  insert hit `media_upload_key_uidx`), it asks once more. The row is then there, so `ops_save_media` answers
  `{id, created: false}` and the client's existing `created === false` path shows the stored row. Exactly one retry;
  any other error is not retried; a second 23505 goes to the wrapper as before (409).
- The client's `slug_taken` branch (`use-media-library.ts:185`) is left as the fallback for that second 23505.

## Grok's medium (controller, 2026-10-13): "middleware clones the whole upload body"

Answer: **the clone Grok names does not run on Workers, and excluding the route from the matcher would not remove the
copies that do happen.** No code change for it; one edge measurement before go-live (controller step 3).

- On Cloudflare the Worker runs OpenNext's routing layer first (`node_modules/@opennextjs/cloudflare/dist/cli/templates/worker.js:34`,
  `middlewareHandler(request)`), then the server function (`:41`). Both use the edge converter, which for every
  non-GET request does `Buffer.from(await event.arrayBuffer())`
  (`node_modules/@opennextjs/aws/dist/overrides/converters/edge.js:19-21`; built: `.open-next/middleware/handler.mjs:439`).
  That read happens for every non-GET request **whatever `middleware.ts`'s matcher says**, and the routing layer passes
  the body on as a `Request` built from that Buffer, which the server converter reads again: two whole-body reads.
- Next's middleware gets a one-chunk stream over that Buffer
  (`node_modules/@opennextjs/aws/dist/core/routing/util.js:197`, `convertBodyToReadableStream`) and does not read it.
  Next's `getCloneableBody` is not in the middleware bundle (`grep -c` = 0). In the server bundle it is only wired by
  `NextNodeServer`, and `cloneBodyStream()` is called only for in-process middleware, which OpenNext removes.
- So moving the owner check into the route and dropping `/api/ops/media` from the matcher would save the Next
  middleware run (one Supabase `getUser` round trip), not a byte of body copying. The only way to take the body out
  of OpenNext is a different upload path, which is a design decision, not this fix-up:
  (a) `worker/almar-ops.mjs` answers `PUT /api/ops/media` itself and streams `request.body` to `env.MEDIA`, with an
  owner check in the Worker entry (a second owner gate to keep identical to `requireOwner`); or
  (b) the browser uploads straight to R2 with a short-lived signed URL from the owner API (needs an R2 API token
  secret: an owner gate).
- Measured, locally (`tests/build/media-put-cpu.mjs`: built `almar-ops` under `wrangler dev`, V8 profiler over the
  inspector, sampling 50 µs, owner session on the local stack; non-idle sampled ms / wall ms):

  | request | run 1 (≈16:39, 3 each) | run 2 (≈16:41, 3 each, load average 12–17 after the reboot) |
  |---|---|---|
  | GET list (one page) | 59 / 62 | 328 / 344 |
  | PUT 1 KB → 200 | 49–77 / 50–78 | 141–361 / 205–371 |
  | PUT 10 MB → 200 | 51–170 / 158–173 | 194–584 / 519–588 |
  | PUT 10 MB + 1 → 413 | 75–97 / 89–102 | 168–373 / 195–409 |

  Earlier full run (≈16:38, sizes 1 KB…10 MB, 3 each): 1 KB 67–124, 1 MB 96–226, 4 MB 155–237, 8 MB 179–216,
  10 MB 79–197 sampled ms. `arrayBuffer` frames: ~0.7 ms at 1 MB, 9–11 ms at 8–10 MB, 11–12 ms on the 413.
- What the numbers show: workerd does not mark idle for the profiler, so sampled ≈ wall and includes waiting on the
  loopback socket, the local R2 simulator and Supabase; a 1 KB PUT and a one-page GET already "sample" 50–360 ms.
  **These numbers cannot say whether a 10 MB upload stays under the Free plan's 10 ms on the edge**, in either
  direction. The size-dependent part is native (no JS frame), in OpenNext's reads and the R2 put stream, and it is
  paid even by a 413 refusal (the body is read before the route answers). `wrangler.ops.toml` sets no `[limits]`.
