## Build shell: what a build may and may not see (reconciliation with job 10)

Job 10's `assertNoPublicEnv` refused every `NEXT_PUBLIC_*` in the build shell, because Next inlines those values as strings. This plan needs the project's public URL and anon key at build time. The two rules are now one rule, and the plan did settle it (no stop needed):

- **The shell that runs `node scripts/assemble-cloudflare.mjs` may hold exactly two `NEXT_PUBLIC_*` names:** `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Any other `NEXT_PUBLIC_*` is refused (job 10's rule, unchanged for every other name).
- **Next and OpenNext never see those two names.** `nextBuildEnv` (in the assembler) removes every `NEXT_PUBLIC_*` from the environment of `opennextjs-cloudflare build` and passes the two values as `ALMAR_BUILD_SUPABASE_URL` and `ALMAR_BUILD_SUPABASE_ANON_KEY`, plus `ALMAR_DATA_SOURCE`. Measured: when Next does see the NEXT_PUBLIC names it writes their values as strings into the server chunks, middleware and OpenNext bundles (not into `out/` or `.next/static`). That would make the Worker ignore its own secrets at request time and put the project address and anon key into `almar-preview`, which holds no secrets on purpose (fail closed). With the hand-over names nothing is inlined and every Worker still reads its Worker secrets at request time. `parity-build` scans `out/`, `.next/static`, `.next/server` and `.open-next` for the anon key and fails on a hit; the last run found none.
- **The service-role key can never reach a build.** The assembler refuses any variable whose name matches `SERVICE_ROLE` and has a non-empty value (`assertNoServiceKey`, extra mitigation for T-3.2-10); `lib/data/source.ts` imports no sibling module and never `lib/supabase/clients`; `tests/secrets.test.mjs` fails if lib/data imports the server clients or names a service key, or if the assembler names `SUPABASE_SERVICE_ROLE_KEY`. Build-time reads use the anon key only (C-04).
- **Assembled targets** (preview, production, ops): `ALMAR_DATA_SOURCE=fixtures`, a mistyped value, `ALMAR_FIXTURE_DIR`, or a missing/blank public name are all refused before anything is built or removed. `--target=local` stays fixtures unless `ALMAR_DATA_SOURCE=supabase`.
- Runbook lines updated: `02-RUNTIME-DEPLOY.md` (build-shell note before the preview and production assemble commands), `03.2-OPS-DEPLOY.md` section 1 step 1, `README.md`. `HANDOVER-job-10.md` is a historic record and is left as written.

Everything above is checked by tests (tests/data-source.test.mjs: allow-list, service-key refusal, `nextBuildEnv`, order of the checks in `main()`; tests/assemble-target.test.mjs; tests/secrets.test.mjs) and by real assembles (below).

## What was built

- `lib/data/source.ts`: `dataSource()` (unset, empty or `fixtures` = fixtures; `supabase`; anything else throws), `loadSource()`, `readSource(name)`, `SOURCE_VIEWS`, `fixtureDir()` (`ALMAR_FIXTURE_DIR`, local builds and tests only). Supabase mode reads 11 views with the anon client (`persistSession:false`), `select("*", {count:"exact"})`, ordered, paged by `.range()` from the number of rows read so far. A page that stops short of the count, a count that changes while reading, an error, or an empty `api_stays` throws, so the build fails and the live site stays as it was (C-03, T-3.2-11). Image alt texts in supabase mode are the database records plus the fixture records of images the database has no record of (the pictures of page blocks that stay fixtures, C-21), never two for one (image_id, locale).
- `lib/data/{stays,destinations,experiences,team,home}.ts` read through `readSource` after `await loadSource()`; `resolve.ts` rebuilds its alt cache when the source array changes; `lib/data/types.ts` and every `components/` and `app/` file are untouched (SC5).
- `scripts/assemble-cloudflare.mjs`: `dataSourceFor`, `nextBuildEnv`, `assertNoServiceKey`, allow-listed `assertNoPublicEnv`; the ops target of 03.2-03 is intact (the ops assemble below).
- `scripts/parity-build.mjs`: build A (live-shaped fixtures, C-16: sample blocked dates dropped, `min_nights` 1) -> reset + import into the local stack under the stack lock -> build B (supabase) -> compare every file byte for byte after the build id is replaced (`"b":"id"` and the `<!--id-->` form with `-` as `_`) -> key scan -> optional build C (today's fixtures, `--against-today`). Final `out/` is build B; the local database is reset to empty at the end. Flags: `--against-today`, `--live`, `--strict`, `--keep`.
- `tests/fixtures-frozen.test.mjs`: sha256 of the canonical JSON of the moved fixtures (destinations, stays, catalogue, team, the three home journeys and their translations) and of the alts of the pictures they reference. A change fails with "this content lives in the database since 3.2: edit it in the dashboard". Page-block fixtures (home hero, about, contact, posts, /destinations hero) are not frozen (C-21).

## What the controller must run with `--live`, and when

`--live` is not run by me. It compares the site built from the LIVE database with the live-shaped fixtures, read-only.

- **When:** after this branch has been checked in a clean clone and before the first deploy of code that reads the database, and in any case before the owner edits any catalogue content in the dashboard. After the first dashboard edit the live rows differ from the fixtures on purpose and the run will (correctly) show differences. The live project holds the 1,127 imported rows since 2026-10-05 18:27 +04, so it can run as soon as the branch is checked.
- **How:** in the clean clone, in a shell that exports exactly `NEXT_PUBLIC_SUPABASE_URL` (the `https://jkdkaldgeiowkhlfmsft.supabase.co` address) and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (the public anon key), with no service-role variable set: `node scripts/parity-build.mjs --live --keep`. No stack, no reset, no import. Only GET requests of the view reads reach the project; build A reads fixtures and makes no request. `--live` refuses a non-hosted URL and any service-role variable.
- **Expected:** `PARITY OK`, 576 files, 0 differing (a handful of home pages may be ORDER ONLY). Any differing file means a live row differs from the fixtures it was imported from: read the printed `DIFFERS` context, do not deploy.
