<decisions>
## Implementation Decisions

### Publish and the public site
- **C-01 (owner):** Publish triggers an **automatic rebuild and redeploy** of the public site. No wait for a
  person after the owner clicks Publish.
- **C-02 (owner):** The rebuild builds from **the code that is live now**: a `live` branch on GitHub that the
  controller moves only on the owner's deploy word. A Publish click therefore changes content only, never code.
  `main` may run ahead of `live`.
- **C-03:** Several Publish clicks within a short window produce one rebuild (debounce; the planner sets the
  window, about 2–5 minutes). The dashboard shows the state of the public site: "Up to date" / "Updating" /
  "Update failed" with the time, so the owner knows when a change is visible. A failed rebuild leaves the live
  site as it was.
- **C-04:** Build-time reads use only the public (anon) Supabase key through published views; no service key in
  the build. The booking path never trusts build-time data for money or availability: it reads live (Phase 4).
- **C-05:** Setting up the rebuild pipeline (Cloudflare build connected to `Loomlyne/almar`, or an equivalent
  trigger) is an **owner gate**: one numbered step. The researcher picks the mechanism; the owner's per-deploy
  rule now has this standing exception: his own Publish click is his word for a content-only deploy.

### Languages
- **C-06 (owner):** An **auto-translate button** in v1. Ops types English; "Translate" fills the Arabic and
  Spanish tabs as drafts that ops can edit before Publish.
- **C-07 (owner):** The translator is **Cloudflare Workers AI** (inside the ALMAR Cloudflare account, no new
  vendor). Needs an AI binding on Worker `almar` (owner gate, and job 10's no-bindings test changes). The
  researcher picks the model and checks Arabic quality on 3 real ALMAR texts before the plan locks it.
- **C-08:** Publish requires all three languages present (EN typed, AR/ES translated or typed). A translated
  record is stored with status `draft` until the owner reviews it; the 3.3 data contract already carries
  `translation_status` (`published` / `draft` / `fallback`). Lock per language (I18N-04) is v1.1.
- **C-09:** Storage stays **one record per language** behind each item (owner, 2026-10-02 15:40), matching the
  3.3 fixtures (`stay-translations`, `catalog-translations`, …). Base tables hold non-text facts.

### Photos
- **C-10 (owner):** Both: **pick from the existing photos** (the 117 on `media.almarprivatejourney.com`) **or
  upload a new one**. Upload goes straight to R2 bucket `almar-media` through the Worker (R2 binding: owner
  gate). Alt text in EN / AR / ES per image (auto-translate applies). Never Supabase Storage.

### Rates and availability
- **C-11 (owner):** **One base nightly rate per stay plus any number of date ranges** with their own nightly
  rate (a season or a single night). The most specific (shortest) range covering a night wins; ranges of the
  same length may not overlap. All in AED.
- **C-12:** A stay with no base rate cannot be booked (STAY-03); the public card keeps its published price
  label. No invented rate anywhere: the import carries `nightly_rate_aed = null` and the owner types real rates.
- **C-13:** Availability per stay: ops blocks full days (D-87, D-63) for one stay, one destination or
  everything, with an optional reason. Paid bookings (Phase 4) also block. Min nights per stay, default 1, no
  max (STAY-06). Pets rule per stay (allowed / not allowed / fee, STAY-05). Infants count toggle per stay.
- **C-14:** Stay access (exact address, wifi, door code) is stored per stay in a table no public view exposes;
  the guest sees it only after the booking is Confirmed (OPS-10, Phase 4 / ops).

### Journeys (Packages)
- **C-15 (owner):** Dashboard → Catalog → Packages **edits the three home journeys**: name, price line,
  description, photo, show/hide, order. They stay "request on WhatsApp"; no package booking in v1. The price
  line is the owner's own text (accepted 2026-10-02), never computed.

### Content import
- **C-16:** Everything the public site shows today from the fixtures is imported into the live database as it
  is published today (same text, same AR/ES records with their status, same images), so swapping the data
  layer changes nothing a visitor sees. Sample values (`is_sample`, e.g. sample blocked dates) are **not**
  imported to live. The Mariven sentence is not carried.
- **C-17:** Team imports empty: the two real members (Maria Del Mar Valdes, María Francis) appear only when the
  owner publishes them (D-57). Fields follow the canvas (name, role, photo, optional email, social links,
  shown, order).

### Dashboard screens
- **C-18:** Screens follow canvas page 7 (dense dashboard variant), D-82 (phone versions), D-88 (side panels),
  D-89 (one experiences-and-services list). Built already wired: no screen ships with a control that does not
  save. Anything not drawn on the canvas gets pictures for the owner's signature before code.
- **C-19:** Writes go through owner-only server endpoints under `/api/ops/*`: each checks the session is the
  owner (`isOwnerProfile`, job 02) on every call, then writes with the service role. A `requireOwner()` helper
  is added once and used everywhere.

### Claude's Discretion
- Exact table and column names, as long as `lib/data/types.ts` shapes are returned unchanged (ROADMAP SC5).
- Debounce window, rebuild status storage, the Workers AI model.
- The 3.1 leftovers assigned to 3.2 (globals.css font sizes, settings hexes, logo `object-left`, `field.tsx`
  labels, harness fixtures in the build) are mechanical; fold them into the screens plan that touches the file.
</decisions>
