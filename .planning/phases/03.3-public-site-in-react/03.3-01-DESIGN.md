**Proposal for the filters, search and the rest.** Built only from existing tokens and the one approved
filter pattern on the canvas — board **5e · Experiences and services** (`PublicExperiences.dc.html`), whose
`expCatalog` the owner approved on 2026-09-29: desktop a 280px filter rail at `gap:48px` with a search
field, vertical type buttons, grouped checkboxes and `Clear filters`; tablet and phone collapse to a search
field plus a `Filters` button with a count badge plus type chips. The filter chip primitive is specified on
**3a · Controls**: a joined `role="group" aria-label="Filter"` row of `aria-pressed` buttons, `height:40px;
padding:0 16px`, joined with no gap, 40px visible and a 44px hit area.

Applied to `/private-stays`, below the `<h1>` and above the grid:

- **Search field.** `Field` with `search`, full content width on phone and 50% on desktop (matching the
  live page's `width:50%`). Label `Search stays` (visible, not placeholder-only — the live page's unlabelled
  input fails the accessibility rule). Matches stay title, neighbourhood and destination name.
- **Destination.** A joined chip row: `All` · `Cartagena` · `Medellín`. Values come from
  `getDestinations()`; only destinations that have a published stay appear. Two chips today.
- **Guests.** A `Stepper` labelled `Guests`, floor 0 (= any). Keeps stays whose `max_guests` is at least the
  number. Reads the derived numeric column, not the published text.
- **Bedrooms.** A joined chip row `Any` · `1–4` · `5–8` · `9+`. `bedrooms` is a clean integer on all 12.
- **Result count.** One line, `12 stays` / `3 stays` / `1 stay`, plural-formed by `formatPlural`, in an
  `aria-live="polite"` region so a screen reader hears the filter work.
- **`Clear filters`.** `Button variant="ghost"`, shown only when a filter is set.
- **Empty state.** When nothing matches: the real line `No stays match these filters.` plus the same
  `Clear filters` control. Not a board pattern, but the same shape as the approved `menu.empty`
  (`No destinations to show.`) and the dashboard's `No … yet` lines.

No sort control: there is no published field to sort by that a visitor would want, and `position` is the
owner's own order. No pagination: 12 cards.

**Card becomes a link.** The whole card is one `<a>` to `/private-stays/<slug>` (locale-prefixed), with the
only hover and focus treatment in the system that is already approved — a gold 1px underline on the title
on hover (`decoration-gold decoration-1 underline-offset-4`, from `components/ui/link.tsx`) and the global
`:focus-visible { outline: 2px solid var(--color-teal); outline-offset: 2px }` from `app/globals.css`.
Nothing new is invented.

**No journey bar on `/private-stays`.** The board has none, and a bar whose Search is held would add
nothing. Instead the hero bar on the home page hands its choice to this page as query parameters
(section 4.2), and this page shows that choice already applied in the filters.

**The detail line on the card.** The board shows one line, and the live cards publish four fields
(bedroom count, neighbourhood, guest label, `On request`). Proposal: one line reading
`<neighbourhood> · <guests_label>` — for example `Casa Centro Getsemani · Up to 10 Guests` — which is real
published content and fits the board's single 14px muted line. The `On request` price label is **not** put
on the card: it is the same five words on all twelve and adds nothing; it stays on the detail page where
the published sentence explains it.

## 3. The data contract — a proposal

**These files are not created by this job.** They are the contract the next job writes. Async, snake_case,
nullable where the column is nullable, ids and timestamps present, so Phase 3.2 swaps fixtures for Supabase
queries by editing only these modules. No component imports a fixture.

3.1 is the load-bearing part: it decides how Arabic and Spanish are stored, shows both candidate shapes, and
sets out why the storage shape cannot leak into a component. 3.9 covers sample data and the three fields
with no source anywhere. 3.10 sets out the image-host options without choosing one.

### 3.1 How the three languages are stored, and why the boundary holds

This is the decision that freezes the Phase 3.2 contract, so it comes first and is settled here.

#### 3.1.1 The two candidate shapes

**Shape A — one translation record per language, behind the entity.** Recommended. A child table per
entity: `stay_translations (stay_id, locale, …text columns…, status, is_locked, updated_at)`, one row per
stay per locale, primary key `(stay_id, locale)`. The parent `stays` row keeps only what is the same in
every language — ids, images, counts, dates, flags, order.

```sql
-- illustrative, not a migration. The controller issues migration numbers.
create table stays (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,
  destination_id uuid not null references destinations(id),
  bedrooms int, bathrooms int, max_guests int, min_guests int,
  min_nights int, nightly_rate_aed numeric,
  blocked_dates date[] not null default '{}',
  is_published boolean not null default false,
  is_sample boolean not null default false,
  position int not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table stay_translations (
  stay_id uuid not null references stays(id) on delete cascade,
  locale text not null check (locale in ('en','ar','es')),
  title text not null,
  tagline text, neighborhood text, guests_label text,
  bathrooms_label text, beds_label text, price_label text, price_note text,
  description text[] not null default '{}',
  amenities text[] not null default '{}',
  inclusions text[] not null default '{}',
  policy_headings text[] not null default '{}',
  -- I18N-04: auto-translated on publish, editable, lockable; English change re-translates unless locked.
  status text not null default 'draft' check (status in ('published','draft')),
  is_locked boolean not null default false,
  updated_at timestamptz not null default now(),
  primary key (stay_id, locale)
);
```

**Shape B — three columns per translatable field on the entity itself:** `title_en`, `title_ar`,
`title_es`, `tagline_en`, … on the `stays` row.

| | Shape A — translation records | Shape B — columns per language |
|---|---|---|
| Columns on `stays` | 12 structural + 12 translatable, in a child table | 12 structural + **36** translatable |
| Adding a fourth language | insert rows; no migration, no code change | a migration adding 12 columns to every entity table, and every query edited |
| I18N-04 (auto-translate on publish, editable, **lockable**, re-translate unless locked) | one `status` and one `is_locked` per language, where they belong | needs `title_ar_locked`, `tagline_ar_locked`, … — 24 extra boolean columns per entity, or it is not expressible |
| Dashboard editing (7k Content, 7h Stays) | a language tab over one record; row-level security per locale is natural | one enormous form, or a hand-built split of 36 fields |
| Query cost | one join on `(stay_id, locale)`, plus one fallback join to `en` | none |
| Supabase generated types | clean named columns on both tables | clean, but 36 of them per entity |
| Missing translation | the row is absent — easy to detect and report | an empty string, indistinguishable from "deliberately blank" |

**Recommendation: Shape A.** Two reasons decide it. First, I18N-04 is a per-language state machine
(*auto-filled* → *edited* → *locked*), and a state machine needs a row to live on; Shape B can only fake it
with a parallel column per field. Second, Arabic and Spanish for the twelve stays do not exist yet (7.2), so
the common case at launch is *a translation row that is missing* — which Shape A represents exactly and
Shape B cannot distinguish from an empty field. The cost is one join, paid once inside `lib/data`.

A third shape — a single `translations jsonb` column holding `{ en: {…}, ar: {…}, es: {…} }` — is rejected:
Supabase's generated types reduce it to `Json`, so every field loses its type; per-field row-level security
for the dashboard is not expressible; and the dashboard would have to read-modify-write the whole blob to
change one line.

#### 3.1.2 The boundary: why the storage shape does not leak

The contract that makes Phase 3.2's criterion 5 achievable is this, and it is deliberate, not hopeful:

**Every module takes a locale and returns rows whose translatable fields are already plain
single-language values.** No type returned by `lib/data/` contains a locale-keyed map, a `*_en` / `*_ar` /
`*_es` field, a `translations` member, or a `locale` parameter on any field. A component receives `title:
string` and `amenities: string[]` — nothing more. It cannot therefore depend on how those strings were
stored, and Shape A, Shape B or the rejected jsonb shape can each satisfy the same signatures.

Two things come back alongside the text so a page can be honest without knowing the storage:
`locale` (which language this row's text is in — it may differ from the one asked for) and
`translation_status`.

**This is enforced by a test, not by good intentions.** A node test fails if any file under `components/`
or `app/` contains `_ar`, `_es`, `_en` as a field suffix, the identifier `translations`, or an import from
`lib/data/fixtures/`. That test is what turns criterion 5 from a hope into a gate, and it should be written
in this slice, with the data layer, rather than discovered to be missing in Phase 3.2.

**The fixtures mirror the chosen storage shape, not the resolved shape.** `lib/data/fixtures/stays.json`
holds base rows and `stay-translations.json` holds one record per stay per locale. The resolution and
fallback code inside `lib/data/stays.ts` is therefore written once, in this slice, and survives the swap
untouched; only the fetch changes, from `readFile` to `supabase.from("stays").select(…)`. If the fixtures
instead held already-resolved per-locale objects, Phase 3.2 would have to write the resolution logic from
scratch and criterion 5 would be at risk again.

#### 3.1.3 The shared types

```ts
// lib/data/types.ts

export type Locale = "en" | "ar" | "es";

/** Supabase uuid. */
export type Uuid = string;
/** Supabase timestamptz, ISO 8601 with offset: "2026-10-02T11:00:00+00:00". */
export type Timestamp = string;
/** Supabase date, ISO 8601 calendar date: "2026-10-19". */
export type IsoDate = string;

/**
 * The state of the text on this row, for the locale that was asked for.
 * "published" — a translation record exists and the owner has reviewed it (status = 'published').
 * "draft"     — a translation record exists but is a machine draft (status = 'draft').
 * "fallback"  — no translation record for that locale; the English text was returned instead.
 */
export type TranslationStatus = "published" | "draft" | "fallback";

/** Every row the data layer returns carries these. */
export type RowMeta = {
  id: Uuid;
  created_at: Timestamp;
  updated_at: Timestamp;
  /**
   * The locale this row's text is actually in. Equals the locale asked for unless
   * translation_status is "fallback", in which case it is "en".
   */
  locale: Locale;
  translation_status: TranslationStatus;
  /**
   * True while any value on this row is sample data rather than published content.
   * A real boolean column in Supabase, default false, so a seeded demo row stays
   * identifiable after the fixtures are swapped out. See section 3.9.
   */
  is_sample: boolean;
  /**
   * Exactly which fields on this row hold sample values. Empty on a fully published row.
   * A money field may never appear here — asserted in tests (3.9).
   */
  sample_fields: string[];
};

/**
 * Media. See section 3.10 on where these files are served from — that is not settled.
 * In Supabase this is an https URL only (R2 / Cloudflare, never Supabase Storage, which is off).
 */
export type ImageRef = {
  id: Uuid;
  url: string;
  /** Resolved for the requested locale. An image with text in it needs three files; others share one. */
  alt: string;
  width: number | null;
  height: number | null;
  position: number;
};
```

Note what is **not** in these types: no `title_ar`, no `translations`, no `Record<Locale, …>`. That absence
is the contract.

### 3.9 Sample data, and the three fields that have no source

Fixtures are sample data by definition. Without a flag, an invented number can survive the swap into the
live database and nobody notices. So `is_sample` and `sample_fields` are on `RowMeta` from the start
(3.1.3), they are real Supabase columns, and three tests hold the line.

**The three fields on `Stay` with no source anywhere in the repo, the twelve live pages included:**

| Field | What exists in the repo | Fixture value | Classification |
|---|---|---|---|
| `nightly_rate_aed` | Nothing. `USD` and `AED` appear **zero times** on all 12 detail pages. The only price copy is `On request` on the list card and the published sentence `Public rates are quoted on request. ALMAR confirms availability, staffing, and final pricing before you travel.` | **`null` on all 12** | Never sample. Money is never invented. |
| `min_nights` | Nothing. STAY-06 states the rule (default 1, no maximum) but no per-stay value is published. | **`null` on all 12** | Not sample — absent. |
| `blocked_dates` | Nothing. `blocked`, `unavailable`, `Check in`, `Nights`, `per night` all appear zero times on all 12 pages. Board 5i draws struck-through days and says in its own footnote: *"Blocked dates here are examples."* | A short sample set per stay | **Sample.** `is_sample: true`, `sample_fields: ["blocked_dates"]` |

`blocked_dates` must carry sample values, because it is the one field that makes a rendered control
demonstrably work: without a blocked day, the stay page's calendar cannot be shown to be reading per-stay
availability at all, and the control would be unprovable rather than fake. Flagging it is what keeps that
honest.

**Derived is not the same as sample.** `max_guests`, `min_guests` and the numeric `bathrooms` are *read out
of published text* (`Up to 10 Guests` → 10; `16–20 Guests` → 16 and 20; `8, 1 social` → 8). They are
recorded as derived, not sample, and the published text stays in `guests_label` / `bathrooms_label` and is
what the page shows. The derivation rule for ranges is the one open question on them (7.5).

**Three tests:**

1. No fixture row may have a non-null money field (`nightly_rate_aed`, `price_aed`, `price_from`,
   `price_estimate`) while `is_sample` is true — and no money field name may ever appear in any row's
   `sample_fields`. Money is published or absent; it is never sample.
2. Every field named in a row's `sample_fields` must exist on that row's type, and `is_sample` must be true
   if and only if `sample_fields` is non-empty.
3. The three home tier `price_label` strings must match `lib/copy/home.ts` byte for byte, in all three
   locales. That is what stops an owner-accepted price drifting.

**What the owner must supply later**, and must never be guessed: the nightly rate per stay, the minimum
nights per stay, and the real blocked dates. All three arrive through Dashboard › Catalog › Stays in Phase
3.2, which is exactly where board 5i's footnote already says they belong. Until then the stay page shows
the published `On request` sentence and no amount, which is what the live site says today.

## 5. The locale shape

Decided by the owner on 2026-10-02 ~14:05: EN / AR / ES are per-locale URLs baked at build time, English
at the root. Routing was measured and is settled. This section is the concrete shape.

### 5.1 Route structure

Three literal trees over one shared page component each. Nine route files for three page types.

```
app/
  page.tsx                                  ->  /                             (en)
  private-stays/page.tsx                    ->  /private-stays                (en)
  private-stays/[stay]/page.tsx             ->  /private-stays/<slug>         (en)  generateStaticParams
  ar/page.tsx                               ->  /ar/                          (ar)
  ar/private-stays/page.tsx                 ->  /ar/private-stays             (ar)
  ar/private-stays/[stay]/page.tsx          ->  /ar/private-stays/<slug>      (ar)  generateStaticParams
  es/page.tsx                               ->  /es/                          (es)
  es/private-stays/page.tsx                 ->  /es/private-stays             (es)
  es/private-stays/[stay]/page.tsx          ->  /es/private-stays/<slug>      (es)  generateStaticParams
```

Each of the nine is three or four lines: it imports the one shared page component, binds its locale, and
re-exports `generateStaticParams` and `generateMetadata`. The page components live outside `app/`
(for example `components/pages/home-page.tsx`), so there is exactly one implementation of each page.

**Why literal trees and not `app/[locale]/…`.** A dynamic segment at the root would also match `/about`,
`/contact` and `/private-stays`, colliding with the twelve literal Framer `route.ts` directories that stay
in place through this slice. Literal trees also match the pattern the repo already uses — every one of
today's 26 pages is a literal directory — and need no change to the route resolver in
`tests/no-dead-links.test.mjs` beyond teaching it about `page.tsx`.

**14 pages → 42 documents:** 3 locales × (1 home + 1 list + 12 details). The 12 remaining Framer pages are
untouched and stay English-only; they get no `hreflang`, correctly, because they have no AR or ES version.

The 14 Framer route files they replace are deleted in the code job: `app/route.ts`,
`app/private-stays/route.ts` and the 12 `app/private-stays/<slug>/route.ts`.

### 5.2 `lang`, `dir` and fonts, server-side

`app/layout.tsx` hard-codes `lang="en" dir="ltr"` today and attaches only the two Latin faces. It becomes
locale-aware: `lang` and `dir` from the route segment, and the two Noto Arabic faces
(`notoNaskh`, `notoSans` from `lib/fonts.ts`) attached to `<html>` on the AR documents **at build time**
instead of being added by `setDocumentLocale` after hydration. Arabic is then RTL in the served HTML, from
the first paint, with no flash — which is the whole point of the decision.

Nothing in `app/globals.css` changes: `@custom-variant ar (&:where(:lang(ar), :lang(ar) *))` on line 4 and
Tailwind's built-in `rtl:` both read the html attributes, so every `ar:` and `rtl:` utility already in the
library starts working.

### 5.3 The switcher, and the asymmetric canonicalisation

Measured on 2026-10-02 and confirmed against Cloudflare's static-assets docs for
`html_handling = "auto-trailing-slash"`: a page canonicalises **without** a trailing slash
(`/ar/about/` → 307 → `/ar/about`), a locale root canonicalises **with** one (`/ar` → 307 → `/ar/`).
Because individual files are served without a trailing slash and folder index files with one.

One helper owns this, and the switcher, every internal link, `canonical`, `og:url` and every `hreflang` all
go through it, so a language switch never costs a redirect:

```ts
/**
 * en:            "/"  ->  "/"                "/private-stays"  ->  "/private-stays"
 * ar / es:       "/"  ->  "/ar/"             "/private-stays"  ->  "/ar/private-stays"
 * The trailing slash on a locale home and its absence on a page are both required (measured 2026-10-02).
 */
function localePath(locale: Locale, path: string): string {
  if (locale === "en") return path;
  return path === "/" ? `/${locale}/` : `/${locale}${path}`;
}
```

Its inverse strips a known locale prefix so the switcher can rebuild the current page in another language.
Both directions are asserted in a unit test: for each of the three locales, `/`, `/private-stays` and
`/private-stays/getsemani-colonial-house` round-trip, and the locale home keeps its slash while a page has
none.

`hreflang` on all 42 documents — four tags each, the three locales plus `x-default` pointing at English:

```html
<link rel="alternate" hreflang="en"        href="https://almarprivatejourney.com/private-stays">
<link rel="alternate" hreflang="ar"        href="https://almarprivatejourney.com/ar/private-stays">
<link rel="alternate" hreflang="es"        href="https://almarprivatejourney.com/es/private-stays">
<link rel="alternate" hreflang="x-default" href="https://almarprivatejourney.com/private-stays">
```

The `almar-locale` cookie becomes a remembered preference. It cannot redirect a first visit at the edge:
the deploy is Workers Static Assets with no worker script, so there is nothing to run a redirect in, and
`_headers` sets no `Vary: Cookie`, so a cookie-driven redirect would be cached for the wrong visitor. The
honest alternatives are a small client-side redirect on the English root only, or nothing. **Proposal:
nothing in slice 1.** The switcher is visible, `hreflang` tells crawlers, and a silent redirect that
contradicts a shared link is worse than none. The nine dashboard cookie reads are a different surface and
are not touched by this slice.

### 5.4 The build: `scripts/assemble-cloudflare.mjs`

It harvests `.body` files from `.next/server/app` and mirrors the directory into `out/`, creating
directories as it goes (line 41). Nested locale paths therefore need **no change**: `/ar/private-stays` and
`/ar/private-stays/<slug>` land correctly as they are. Two changes are needed:

1. **The locale root must be an `index.html`.** Today the only special case is `rel === "index"` →
   `out/index.html`, so `app/ar/page.tsx` would land at `out/ar.html`. Measured: a locale with no
   `index.html` is a hard 404 for both `/es` and `/es/`. The rule becomes: a `.body` whose relative path is
   exactly a locale code is written to `out/<locale>/index.html` and **never** to `out/<locale>.html`,
   so the two can never both exist.
2. **Three branded 404s.** `out/404.html`, `out/ar/404.html`, `out/es/404.html`. Cloudflare serves the
   nearest `404.html` walking up the tree, so each locale gets a 404 in its own language and direction with
   no runtime. `renderStaticNotFound()` in `lib/not-found-document.ts` is hardcoded
   `<html lang="en" dir="ltr">` with an English title, heading, link label and `href="/"`; it takes a
   locale and reads its four strings from `lib/copy`, with the home link going through `localePath`.

Careful: `tests/assemble-404.test.mjs` asserts on the **source text** of the assemble script — it must not
contain `app/[...not_found]/route.ts` and must not contain `` const HTML = ` ``. The locale 404s must
therefore be produced by calling `renderStaticNotFound(locale)`, never by an inline template in the script.
The same test must be extended to cover all three 404s and to assert each one's `lang` and `dir`.

The script's only completeness check is that `index.html` and `404.html` exist. It should also assert the
expected document count for the slice (42 plus the 12 remaining Framer pages), or all 28 AR and ES
documents could go missing silently.

`wrangler.toml` is unchanged — confirmed by the measurement. `next.config.ts` is unchanged: no `output`,
no `trailingSlash`, no `i18n` (which is App-Router-incompatible anyway).

### 5.5 Working with JavaScript off

The 42 documents are static HTML with the right `lang` and `dir`, so all the content and every link works
with no JavaScript. Two controls do not, because they are Radix listboxes — as is every select in the
system today, the dashboard included: the language select and the currency select.

For language that matters, because it is how a visitor reaches their own language. Proposal: a plain row of

alone, which leaves a no-JavaScript visitor with no way to switch.

For currency it does not matter: with no JavaScript the published price string shows, which is the
owner-accepted text. That is honest, not broken.
