# 03.3-26 SUMMARY: the Contact inquiry form

The Contact page (EN, AR, ES) now has a working inquiry form. After hydration, the end column of the two equal
columns holds the framed teal box: a visually hidden `<h2>`, Name + Phone side by side from md, Email, Journey Type
(slice 1's Select), the message, the 11 honeypots, then `Request Consultation` and `Message on WhatsApp`. A valid
submit POSTs urlencoded to `POST /api/contact`, which sends ONE plain-text email through Resend: from and to
`inquiries@almarprivatejourney.com`, reply-to the visitor. Travel With Confidence is now its own centred section
below the columns, with the outlined `Start Your Inquiry` (a link to `#inquiry`), and job 11's divider after it.
With JavaScript off there is no box, no form and no Start link; the details' WhatsApp row still works.

## Deviations from the plan (and why)

1. **Copy is the owner's signed set** (`s3-pictures/partb-states.json`), not the plan's drafts. Spanish uses "tú" (not
   "ustedes"). New key `form.sending` is the busy label. `failed` is one template with `{email}` and `{whatsapp}`
   plus `whatsappWord`; once filled it equals the signed five parts joined, which a test checks. `tooLong` uses
   `{max}`. There is no privacy or consent line.
2. **Sent state as signed:** one `role=status` line (`font-display text-title text-teal`, focused) replaces the whole
   box, `Message on WhatsApp` included. The box keeps its id and its hidden h2.
3. **Rate limit added** (owner hardening, outside the plan): `lib/form-rate-limit.ts`, the `[[ratelimits]]` block, and
   429 placed between size and honeypots. It **fails open**: no binding (next dev, node) or a limiter that throws
   lets the post through, so a binding problem cannot turn every inquiry away. The reviewer should confirm that
   choice (see Risks).
4. **No `framed-box.tsx` primitive** (controller's preference): a plain bordered div.
5. **`contact-details.tsx` edited**, though the plan listed only `inquiry-form.tsx` as this plan's file in
   `components/pages/contact/*`. Removing `Message on WhatsApp` from under the details requires it.
6. **Prop renamed `newTabLabel`:** `tests/site-footer-copy.test.mjs` forbids the text `newTab:` in `components/pages/**`.
7. **The `#inquiry` hash scroll lives in `InquiryForm`, not `InquiryStart`:** the box owns the ref and exists only
   after mount.
8. **Route body reader:** a capped streaming reader (the same shape as `lib/booking/http.ts`) instead of
   `request.text()`, so a chunked body without Content-Length is still capped. A UTF-8 decode failure is 400.
9. **Test helper added:** `tests/helpers/load-ts-in-repo.mjs` bundles into `node_modules/.cache/almar-tests/` so
   `resend` and `@opennextjs/cloudflare` resolve. With `fakeCloudflare: true` it swaps the OpenNext package for a
   stand-in that binds a fake `FORM_LIMITER`. `load-ts.mjs` is untouched.
10. **Worker-file tests pinned:** `tests/server-runtime.test.mjs` gained one test (the only binding besides ASSETS is
    this exact `FORM_LIMITER` block, in both files). `tests/ops-runtime.test.mjs` had one test title corrected ("bind
    only ASSETS and FORM_LIMITER"); its assertions are unchanged.
11. **Item 10 layout fact:** `Request Consultation` and `Message on WhatsApp` share one row at 834 in all languages
    and at 1440 in EN and AR. **In ES at 1440 they wrap**: 497 px of buttons and gap in a 492 px box (measured on next
    dev). The spec encodes this with a comment. It is the owner's call whether that matters (signed picture vs build).
12. **Served HTML:** it holds no `<form>` and no form markup. The form strings, including "Start Your Inquiry", are
    still in the bytes inside Next's flight payload (`self.__next_f`), because they are props of a client
    component. The plan's acceptance line "out/contact.html contains no Start Your Inquiry" therefore holds for the
    DOM, which is what the JavaScript-off specs check, but NOT for a raw byte grep. `tests/build/contact/built-documents.test.mjs`
    (`<form`, `type="submit"`, `type="email"`, `<textarea`) is unaffected.
13. **Task 4 (the Opus security review) was not run here**, as instructed; the lead runs a fresh reviewer.

## Risks for the reviewer

- The limiter fails open (deviation 3). Fail-closed would block every inquiry if the binding broke.
- Both Workers use `namespace_id = "1001"`. Rate-limit namespaces are per account, so preview and live share counters
  for the same visitor address. That is harmless at 5 a minute; use `"1002"` in preview if they should be separate.
- The origin check compares hosts (Origin host == URL host or Host header), not the scheme, so `wrangler dev`'s http
  works. A non-browser client can forge Origin; the limiter and honeypots are the layers for that.
- Resend SDK 6.29.0 logs its own `[Resend API Error]` object when `NODE_ENV !== "production"` (next dev only). In
  production (Workers) it does not. The API's error text is not ours to control.
- Key trimming: the route uses `process.env.RESEND_API_KEY?.trim()`, as the newsletter route does.
