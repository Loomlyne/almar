## Deviations (and why)

1. **Copy is the owner's signed set** (`partb-states.json`), not the plan's drafts. Public Spanish uses *tú*. The ES
   description and invalid line are pinned to the signed lines (and to the JSON), not to `FRAMER_SOURCE_COPY.es` or
   `HOME_COPY.es.emailError`. EN and AR are still pinned to those sources, where they are equal. `HOME_COPY` and
   `framer-source.ts` are **not** edited. There is no consent or privacy line (owner: Phase 6).
2. **Route hardened and switched on** (owner, 2026-10-14). The plan said "not touched" for the route and both
   Worker files. The address check is `isInquiryEmail` (it needs a dot in the domain, at most 254 characters), and
   the footer adds the same dot rule on top of `checkValidity()`, so `a@b` gets the invalid line, not the failed one.
3. **The assembler's held-path refusal no longer covers `/newsletter`.** In `tests/server-runtime.test.mjs` the two
   assembler cases that used `newsletter.body` and `ar/newsletter.html` now use `dashboard.body` and
   `es/dashboard.html`. Because `run_worker_first` lists `/newsletter`, the Worker answers it first, so a static
   `out/newsletter.html` could never be served there. A `public/ar/newsletter.html` would now ship as a page.
   `scripts/assemble-cloudflare.mjs` was not edited. **Proposal:** the assembler should also refuse a static file at
   any `SERVER_PATHS_OUTSIDE_API` path, with or without a locale.
4. **Column layout:** Pages, Contact, Newsletter from `@2xl` (834). The mock's four columns (with an empty third)
   apply only from `@6xl` (1440). At 834, four columns would leave about 170 px for the box and the button.
5. The scene's `border-t border-line pt-8` on the newsletter cell is the sheet's separator, so it was not copied.
   The failed line sets `aria-invalid` on the box, as the scene draws state 10.
6. The teal (default) footer gets the same flow with its old ivory styles. Only the harness uses it.
7. **Harness scenes:** `newsletter-light` (resolves after 300 ms), `newsletter-fails` and `newsletter-honeypot`.
   `newsletter-on` and `newsletter-no-handler` are unchanged, and `tests/ui/extensions.spec.ts` is unedited.
8. **Shared footer assertion:** `tests/build/newsletter/_footer.ts` (new) holds `expectFooterNewsletter` and
   `OUTSIDE_FOOTER`, so every held spec makes the same one assertion.
9. **Menu locators made `exact: true`** in `tests/build/slice3-pages.ts` (`openMenu`), `tests/ui/about-page.spec.ts`
   and `tests/ui/contact-page.spec.ts`. The AR button `انضموا إلى القائمة` contains the AR Menu word `القائمة`, so a
   substring match hit both buttons. Found by running `tests/ui/about-page.spec.ts`: 4 failures, all AR at 390/834.
10. **Added `tests/public-frame-render.test.mjs`** with one test: the served markup of `PublicFrame`, with the real
    table in EN/AR/ES, has no `<form`, no column, no box, no trap and no Join the List.
11. **Build spec items:** item 7 (no other host) is folded into item 2. The failure branches are 400, 404 (HTML),
    429, 500, 502, 503, 200 with `{"ok":false}`, 200 HTML, and network abort.

## Risks for the reviewer

- The limiter fails open, as plan 26's does. `contact` and `newsletter` share namespace `1001`, but the key starts
  with the scope, so their counters stay separate.
- Anyone can subscribe someone else's address: there is no double opt-in (T-3.3-27-06). The rate limit, the Origin
  check and the honeypots limit the volume. A non-browser client can forge Origin.
- The `:not(footer *)` selectors in the specs need Chromium's complex `:not()` (supported). The toast region is
  `fixed` inside the footer's `@container`. It was measured that `container-type: inline-size` does not make the
  footer a containing block for it.
